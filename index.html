Software Design and Engineering

Contact Service

JavaSpring BootMavenJUnitOpenAPI

I took a small application that stored and validated contact records and rebuilt it as a service with clear boundaries between HTTP requests, business rules, and storage. The original contact rules stayed in place while the architecture became easier to maintain and test.

What I changed

  • Introduced controller, service, repository, model, and request and response layers.
  • Added REST operations, consistent error responses, validation, and HTTP Basic authentication.

Artifact Description

The artifact I selected for the software design and engineering category is the Contact Service application that I originally created in CS 320 during 2025. The original program was a small Java application that stored contact records in memory. Each record included a contact ID, first name, last name, phone number, and address. The program could add, update, and delete contacts, and it included JUnit tests for the Contact and ContactService classes. Its validation rules prevented empty values, limited field lengths, required a ten digit phone number, and kept each contact ID unique. The project was useful for demonstrating unit testing and basic object oriented design, but its original structure was limited to a model class and a service class. It did not provide a web interface, separate storage concerns, standardized error responses, access control, or an automated build workflow.

Reason for Selection and Enhancement

I selected the Contact Service because it gave me a clear starting point that could be improved in ways that are common in professional software development. The original version already had a focused purpose and a set of business rules, so I could preserve its intended behavior while redesigning the system around a more maintainable architecture. This made the artifact a good way to show growth beyond writing a few working Java classes. It allowed me to demonstrate how I can analyze an existing program, identify its limitations, and turn it into a service that is easier to test, secure, document, and extend.

The enhanced artifact is a Spring Boot REST application organized into controller, service, repository, model, data transfer object, exception, and configuration layers. The controller exposes HTTP endpoints for creating, reading, updating, and deleting contacts. The service layer contains the business logic, while the repository interface separates that logic from the current in memory storage implementation. This separation is important because a database can be added later without requiring the controller or the contact rules to be rewritten. Request and response objects also keep the external API separate from the internal domain model. Together, these decisions reduce coupling and give each class a specific responsibility.

I also strengthened reliability and security. Contact IDs remain immutable, duplicate IDs are rejected, and all required fields are validated before data reaches the service. A global exception handler returns consistent responses for invalid input, missing contacts, duplicate contacts, and unexpected errors. HTTP Basic authentication protects every endpoint, and credentials are read from environment variables instead of being placed directly in the source code. Application logs record contact IDs and operation results without recording names, phone numbers, addresses, or passwords. OpenAPI and Swagger documentation make the service easier to understand and test. A Maven build and GitHub Actions workflow provide repeatable compilation and automated testing.

The final test suite contains seventeen tests across the model, service, and HTTP layers. These tests cover valid and invalid contact data, duplicate detection, updates, deletion, missing records, authentication, validation failures, and successful REST requests. All seventeen tests pass with no failures, errors, or skipped tests. This broader coverage demonstrates that the enhancement is not only a structural redesign. It verifies the behavior that users and other systems would depend on.

Course Outcomes

The enhancement met the four course outcomes that I identified in Module One. For course outcome two, the REST interface, consistent response format, project README, and OpenAPI documentation provide professional written and technical communication for developers who need to use or maintain the service. The organization and naming of the code also communicate the role of each component more clearly than the original two class design.

For course outcome three, I designed a solution that addresses the original problem while considering the tradeoffs involved in the design. I kept an in memory repository so the milestone could remain focused on architecture and application behavior, but I placed that implementation behind a repository interface. This choice keeps the current solution simple while leaving a practical path to persistent storage. I also used immutable contact IDs, clear validation boundaries, and sorted list results so the service behaves predictably.

For course outcome four, I used current tools and techniques to deliver a more complete computing solution. Spring Boot provides the application framework, Maven manages dependencies and the build, JUnit and Spring testing tools verify behavior, and the continuous integration workflow runs the test suite whenever changes are submitted. The combination of layered design, automated tests, API documentation, and repeatable builds shows how development tools can work together to produce value instead of functioning as isolated project features.

For course outcome five, the enhanced service demonstrates a stronger security mindset. Authentication limits access to the API, request validation rejects malformed data, externalized credentials reduce the risk of exposing secrets in the repository, and careful logging avoids disclosing private contact information. The exception handler gives clients useful information without returning internal stack traces. I did not need to change the outcome coverage plan from Module One, although the finished artifact addresses security more thoroughly than the original version did.

Reflection on the Enhancement Process

The most important lesson from this enhancement was that software quality depends on the boundaries between components as much as it depends on the code inside each method. In the original project, storage and business operations were handled together. As the application grew into a REST service, that approach would have made validation, error handling, and testing difficult to manage. Separating the controller, service, and repository helped me reason about one concern at a time. It also made the tests more meaningful because I could test business rules without starting a web server and then test the HTTP contract separately.

One challenge was turning a small Java project with no formal build configuration into a complete Spring Boot application. I had to establish the package structure, define dependencies, preserve the original validation requirements, and decide which layer should enforce each rule. I learned that the API should reject bad requests early, while the domain model should still protect its own invariants. Using both request validation and model validation provides a safer design because the model remains valid even if it is created somewhere other than the controller.

Testing also revealed an environment specific issue with the default Mockito engine, which attempted to attach an agent that was not supported in the restricted test environment. I researched the failure and configured Mockito to use its subclass engine instead. That change preserved the intent of the tests and allowed the full suite to run successfully. This challenge reminded me that debugging often requires separating an application defect from a tool or environment limitation. The final passing build gave me confidence that the service behavior remained correct after the adjustment.

If I continued this project, the next logical step would be to connect the repository interface to a persistent database and replace basic authentication with a token based approach and role based authorization. I would also add deployment configuration and monitor the service in a hosted environment. For this milestone, however, the finished enhancement accomplishes the planned goal. It transforms the Contact Service from a classroom example into a documented, tested, secured, and maintainable REST API that better reflects the software design and engineering skills I have developed throughout the program.

Pirate Intelligent Agent

PythonNumPyTensorFlowKerasDeep Q Learning

This project trains an agent to navigate an 8 by 8 maze. I selected it because it connects algorithmic decisions with measurable behavior and uses stored experiences to improve the learning process.

What I changed

  • Limited action selection to valid moves in the current maze position.
  • Expanded replay memory and delayed training until enough experiences were available.
  • Added scheduled target network synchronization and gradual exploration decay.
  • Tracked win rate, training loss, steps, rewards, and exploration values.
  • Integrated the missing maze and replay modules into a more portable project.

What I learned

The largest lesson was that an algorithm should be evaluated through evidence, not just whether one run succeeds. Rebuilding the missing supporting modules also made me understand how the environment and memory structures affect training.

I selected this artifact because it demonstrates how algorithms, data structures, and machine learning can work together to solve a navigation problem. The experience replay structure stores previous state transitions so they can be sampled again during training, while the Q network evaluates possible actions. For the enhancement, I restricted exploitation to actions that are valid in the current maze position, increased replay memory capacity, delayed training until enough experiences have been collected, and added scheduled target network synchronization. I also changed exploration so epsilon decays gradually to a minimum value and added repeated completion checks before training can stop. Win rate, loss, epsilon, steps, and reward are now recorded so I can evaluate the training process instead of relying on only one final result. I also added a standalone Python version and setup instructions so the enhanced artifact can be run and tested in Visual Studio Code.

Course Outcomes

This enhancement supports the course outcome of designing and evaluating computing solutions using algorithmic principles and computer science practices. I had to evaluate the original reinforcement learning process, identify weaknesses in action selection and training stability, and improve how the agent learns from stored experiences. It also supports the outcome involving well founded tools and techniques because the project uses Python, NumPy, TensorFlow/Keras, a replay-memory data structure, a target network, and measurable performance history. My outcome coverage plan has not changed significantly, but the enhanced artifact now gives stronger evidence that I can evaluate design trade offs and measure whether an algorithm is improving over time.

Reflection on the Enhancement Process

The main thing I learned is that small changes to an algorithm can make a large difference in how understandable and reliable the training process becomes. Valid action selection prevents the model from choosing an impossible move simply because that output has the highest Q value. The replay buffer and target network also showed me how stored data and controlled updates can make reinforcement learning more stable. A challenge was that the copy of my original artifact no longer included two supporting starter files that the notebook imported. Instead of leaving the project dependent on files I could not submit, I integrated the required environment and replay behavior into the enhanced artifact. That made the project more portable and gave me a better understanding of how those supporting pieces work. I also added a smoke test and a normal Python entry point so I can verify the environment in Visual Studio Code before starting a longer training run.

Artifact Description

The artifact I selected for the databases category is the Grazioso Salvare rescue dashboard that I originally created in CS 340. The application was designed to help an animal rescue organization work with shelter records through a dashboard. The original version connected a Python dashboard to a database and allowed the user to filter animals for different rescue categories, view records in a table, examine breed information in a chart, and display the location of a selected animal on a map. I selected this artifact because it brings together database access, Python programming, data filtering, visualization, and user interaction in one project.

Reason for Inclusion and Improvements

I included this artifact in my ePortfolio because it demonstrates that I can build a program around stored data instead of treating the database as a separate piece. For the enhancement, I rebuilt the data layer so the project can run locally without depending on a separately configured MongoDB server. The enhanced version uses SQLite and automatically creates the database and its schema when the application starts. It also seeds the database with sample shelter records when the database is empty. I created a dedicated AnimalShelter class for database operations and added create, read, update, and delete functionality. The dashboard now includes record maintenance controls so a user can add a new animal, update the selected animal, or delete a selected record. I also added indexes on fields used frequently by the rescue filters and used parameterized SQL statements rather than building SQL directly from user values. These changes make the artifact easier to run, more complete, and better organized while preserving the filtering, chart, table, and map features from the original project.

Course Outcomes

This enhancement supports the course outcomes I intended to demonstrate through the database category. It most directly addresses the outcome of using well founded techniques, skills, and tools in computing practices to implement a solution that provides value and meets an industry related goal. The revised data layer, database schema, indexes, CRUD operations, and dashboard integration show progress toward that outcome. It also supports the security mindset outcome because the database class validates supported fields, uses parameterized queries, requires a filter before update or delete operations, and validates important numeric values through database constraints. I do not need to change my outcome coverage plan for this artifact because the completed enhancement still focuses on database implementation and security while also contributing to software design and professional communication.

Reflection on the Enhancement Process

The biggest lesson from this enhancement was that making a database application easy to run requires more than fixing individual lines of code. The original project depended on components that were no longer included with the artifact, including the database access module, database environment, and data source. Because those pieces were necessary for the dashboard to function, I recreated the missing database layer and made the application self contained. This required me to think about the schema, data types, validation, query behavior, and how the dashboard would respond after records were created, updated, or deleted. One challenge was preserving the rescue filters from the original project while changing the storage technology. I addressed that by keeping the same high level query structure in the AnimalShelter class and translating the supported filters into parameterized SQLite queries. I also had to make sure the table, chart, and map continued to refresh from the current database records. The result is a more maintainable artifact because the database logic is separated from the interface, the program includes the files needed to start with usable data, and the database can be recreated locally when necessary. This enhancement improved my understanding of how database design, application logic, security, and usability all affect the reliability of a complete software system.

My computer science education has changed the way I approach technical problems. Earlier in the program, I was mainly focused on making individual programs work. The projects in this portfolio represent three areas that I consider essential to my development as a computer scientist: software engineering, algorithms, and databases.

Collaboration and Communication

Computer science involves communicating decisions as well as writing code. Throughout the program, I have learned the value of clear documentation, testing expectations, and explaining why one implementation was selected over another. Software Engineering and Design

The biggest shift in my software engineering approach has been learning to design systems that can change without requiring everything to be rewritten. In the original Contact Service project, the core responsibilities were handled by a small number of Java classes. For the capstone, I redesigned the application as a Spring Boot REST service with separate layers for requests, business logic, and storage. I kept the original validation rules and introduced more consistent handling of errors and access to the application.

The enhanced Contact Service also gave me practice using tools that support professional development. That experience reinforced the importance of a repeatable development process and meaningful tests, particularly when a project is being changed rather than written from the beginning.

Algorithms and Data Structures

My Pirate Intelligent Agent project represents the area of computer science that I am most excited to continue exploring. The agent uses deep Q learning to navigate a maze and find treasure. Databases and Security
